# ADR-0026: Rust support

- Status: **accepted** for the language; the rules are in progress
- Date: 2026-11-04

## Context

The SonarQube rule parity effort ([ADR-0007](0007-sonarqube-rule-parity.md))
covers JavaScript/TypeScript, Python, Java, C/C++ and C#. SonarQube also
analyzes Rust, and, as with C#, its rule list and default profile come from
the same server the other languages are measured against: 85 rules, none
deprecated (60 bugs, 25 code smells), 78 of them in "Sonar way".

sonda doesn't parse Rust yet. Rules need a grammar, and the metrics
(functions, complexity, comments, duplication) need Rust's node kinds.

The list is short, and almost all of it is Clippy's lints under SonarQube keys:
`S7436` redundant comparisons, `S7437` manual swaps, `S7456` `skip(0)`,
`S7430` `splitn` with a limit of 0 or 1, and so on. Many of those compare
an operand's type, which a syntax tree doesn't carry. That sets the tiers
below.

sonda's own code is a corpus nobody else has: `sonar-project.properties`
already has SonarQube analyzing `crates/`, so each rule can be checked
against what SonarQube reports on the same commit.

SonarQube's Rust analysis has two sensors: its own, which does the syntax
check (S2260) and cognitive complexity (S3776), and one that runs **Clippy**.
83 of the 85 rules are Clippy lints, and each rule's description links the
lint it is (`self_assignment` for S1656). A rule's behavior is its lint's, as
Clippy documents it.

## Decision

### Grammar

[tree-sitter-rust](https://github.com/tree-sitter/tree-sitter-rust) 0.24.2,
maintained by the tree-sitter organization:
- MIT licensed, like the other grammars;
- generated C plus an external scanner, so it joins the C surface worker
  isolation ([ADR-0003](0003-isolate-parsing.md),
  [ADR-0004](0004-sandbox-workers.md)) contains and the fuzzer exercises.
  The `analyze` fuzz target picks languages from `lang::ALL`, so it covers
  Rust once listed; a Rust seed joins the corpus;
- depends only on `tree-sitter-language`, already in the tree.

rust-analyzer or `rustc` would give real types, but need a toolchain and a
buildable project at scan time, which a single binary can't assume.

### The language

- `Lang::Rust`, id `rust`, for `.rs` files. It goes last in `lang::ALL`,
  whose order is a stable one-byte encoding.
- Metrics map Rust's declarations onto the shared `Syntax` table, settled
  against SonarQube's own numbers for sonda's `crates/` (154 non-test
  files): `fn` items and methods are functions. A closure isn't counted as
  a function, but adds one to cyclomatic complexity and nests its contents
  one level deeper in the enclosing function's cognitive complexity.
  `match` is a switch and every arm is a case, the `_` arm too (C#'s discard
  arm is a default and costs nothing; Rust's wildcard costs one). `loop`
  adds cognitive complexity but no cyclomatic, having no condition. Each of
  these moved a measure from several percent off to nearly exact: lines of
  code, functions and cognitive complexity agree to within 0.1%,
  cyclomatic complexity to 0.3%, comment lines to 1.2%. The rest is
  unexplained; SonarQube's analyzer isn't open to read.
- Rule ids are `rs/...`, in `rules/catalog/rs*.rs`.
- `scripts/sonar_parity.py` maps SonarQube's `rust` language to sonda's
  `rust`.

### Rules

ADR-0007 applies unchanged: clean-room rules from each SonarQube rule's
intent, `sonar` references by key, a false-positive review on real code, a
timing check, and on by default only when SonarQube's default profile
enables the key (so 78 of the 85). That applies to the `common/` rules
too: only `common/cognitive-complexity` (S3776) and
`common/too-many-parameters` (S107) have Rust keys, so the other
`common/` rules on by default (function length, TODO comments,
commented-out code) skip Rust.

By the analysis each rule needs, as a first guess ADR-0007 asks to confirm
as each is implemented:

- **Syntactic**, the bulk: empty statements, self-assignment, identical
  operands and `if`/`else if` conditions, missing final `else`, loops that
  run once, too many parameters, wildcard imports, `println!` as logging,
  cognitive complexity, `skip(0)`, `splitn(0|1)`, manual swaps,
  `visit_str` beside `visit_string`, syntax errors.
- **Declared types**, approximated the way C# does ([ADR-0015](0015-csharp.md)):
  a rule reports only what the file's own declarations prove and is
  `related` to its key when typed analysis would find more. For example
  `to_string()` on a `String`, redundant casts, `#[derive(Ord)]` beside a
  hand-written `PartialOrd`.
- **Left out on purpose**, listed as known gaps with the reason, as C# does,
  where a rule needs what only the compiler knows: which trait a method
  resolves to, `transmute` between layouts, whether a pointer's pointee is
  zero-sized.

The split is a guess from rule names. The first batch settles it; the known
gaps list, not this ADR, is the record of what was left out.

### Delivery

1. This ADR.
2. The language: grammar, `Lang::Rust`, metrics, file discovery, fuzz seed,
   the parity script's mapping and an empty catalog. Only the two common
   rules above report. Done.
3. Rules in batches of about 20, each reviewed on sonda's own `crates/`
   (compared with SonarQube's findings on that commit) and on a few open
   source crates, with a timing check.

### Suppressions

Settled by scanning a project on the server: `#[allow(clippy::self_assignment)]`
silences the finding, an `#[allow(unused)]` doesn't, and **`// NOSONAR` does
not** (the Clippy sensor's findings ignore it). sonda mirrors what silences
there, as it does for C#'s `#pragma`: `#[allow(clippy::lint)]` and
`#[expect(clippy::lint)]`, also inside `#[cfg_attr(..., allow(...))]`, on the
item or statement they're written on; `#![allow(...)]` for the enclosing
module or file; and Clippy's groups (`clippy::all`, `clippy::pedantic`,
...), whose members come from Clippy's own listing. Each Clippy lint maps to
its SonarQube key, so a region silences every sonda rule that references the
key. `// NOSONAR` still silences Rust findings in sonda, as in every other
language it supports; that differs from SonarQube on purpose.

Not covered: a crate-level `#![allow(clippy::...)]` in `lib.rs` or `main.rs`
applies to every module of the crate, and sonda reads one file at a time, so
it silences only its own file. C#'s assembly-level suppressions are carried
as facts to a project pass ([ADR-0020](0020-cross-file-declarations.md));
Rust's could be.

### Validating a rule

Clippy is the oracle: the same lint, run on the same code, says what a rule
should report. A rule that sees only syntax reports less than its lint where
the lint needs a type, and more where a method's name is shared with a
non-std type (`heapless::Vec::resize` returns a `Result`; Clippy checks the
receiver is `std::vec::Vec`). The first batch found both: `MaybeUninit::
uninit().assume_init()` initializes arrays of `MaybeUninit` in `arrayvec` and
`smallvec`, which Clippy allows by type, so that rule reports only where the
type is written. Running Clippy on third-party crates executes their build
scripts and procedural macros, so it is done on code you trust, not on
whatever the registry holds: `tools/clippy-oracle/` runs it in a container.

The first batch was measured that way on 66 crates from the cargo registry
(default features, all targets, each lint forced on, suppressions ignored on
both sides, files Clippy didn't compile left out, derive macros' spans on
struct field definitions set aside). Where the lint's pattern occurs:

| Rule | Precision | Recall | Notes |
|---|---|---|---|
| `else-if-without-else` | 98% | 95% | 175 Clippy findings |
| `match-on-bool` | 94% | 96% | 77 |
| `redundant-field-name` | 92% | 88% | 86; misses are inside macros |
| `let-and-return` | 74% | 89% | 19; the rest is temporaries Clippy knows by type |
| `null-pointer-from-zero` | 100% | 100% | 1 |

The second batch, on 51 crates chosen to contain its patterns:

| Rule | Precision | Recall | Cases |
|---|---|---|---|
| `vec-init-then-push` | 100% | 100% | 42 |
| `inline-without-body` | 100% | 100% | 3 |
| `unreadable-literal` | 92% | 95% | 4,238 |
| `unnecessary-semicolon` | 89% | 85% | 186 |
| `wildcard-import` | 88% | 94% | 343 |
| `print-stdout` | 82% | 81% | 1,206 |
| `derived-hash-with-manual-eq` | 100% | 33% | 3 |
| `reversed-empty-range` | 100% | 44% | 9 |
| `never-loop` | 100% | 43% | 7 |
| `approximate-constant` | 100% | 50% | 6 |
| `uninit-vec`, `no-effect` | 100% | 67%, 50% | 3, 2 |
| `identical-operands` | 100% | 25% | 4 |

Comparing taught what no documentation says, and the rules now do it:
`unreadable_literal` starts at six digits, decimal or hexadecimal, not five;
`vec_init_then_push` needs two pushes after an empty `Vec::new()` or `vec![]`,
never `with_capacity(expr)`; `wildcard_imports` leaves enum globs
(`use Kind::*`, which `enum_glob_use` owns), preludes and test code alone, and
Clippy doesn't print-lint test code either; `derived_hash_with_manual_eq` is
only a hand-written `PartialEq<Self>` beside a derived `Hash`, not the reverse;
and where a finding is reported (the `#[derive]`, the `#[inline]`, the
`Vec::with_capacity`) decides whether a comparison by line agrees.

The recall that was left was mostly one gap: **Clippy lints inside macro
arguments** (`assert!(a == a)`, `debug_assert!`, `format!`), where tree-sitter
keeps raw tokens rather than expressions. See "Macro arguments" below.

The first run of `let-and-return` was 53% precise: Clippy skips an initializer
that holds a temporary which inlining would keep alive past the block's locals
(an `unsafe` block, a borrow, a macro, an `.await`, a chain of three calls),
and the rule now skips those shapes. `skip(0)` stays `related`: `rayon` and
`streaming_iterator` have their own `skip`, which only the receiver's type
tells apart. The other rules had no occurrence in the corpus, so they are
checked by their tests alone.

The third batch (`rs_extra.rs`, 18 more lints plus `rs/parse-failure`, S2260,
off by default) is checked by its tests and by Clippy's own UI fixtures, since
most of its lints are too rare in the registry corpus to measure there.
Known gaps: `overly_complex_bool_expr` needs a truth-table simplification,
and the function forms of `min`/`max`. `invalid_null_ptr_usage` no longer
exists in Clippy, so `rs/null-pointer-argument` can't be measured by the
oracle. Eleven of its rules were rewritten in the fourth batch, against
Clippy's output; see "Probing Clippy".

The fourth batch (`rs_last.rs`: `unit-hash`, `unit-cmp`, `enum-clike-unportable`,
`inverted-saturating-sub`, `while-immutable-condition`, `unused-io-amount`,
`possible-missing-comma`) is the rest of what one file's syntax can show; each
is `related` to its key. On the 693 crates of the cargo registry only
`unused-io-amount` and `unit-cmp` occur (the others are rare), so the rest rely
on their tests. `read`/`write` are names many crates give their own methods
(gimli's `write(&mut self, w)` returns a `Result<()>`), so `unused-io-amount`
reports only in a file that names `std::io` or an async I/O module, and never
on `self`; the first run without that gate had 172 hits, nearly all of them
those. Still unmeasured against Clippy (the oracle needs a container). Not
ported, because each needs a type or a regex engine the syntax doesn't give:
`S1612`, `S1858`, `S2198`, `S5856`, `S7411`, `S7412`, `S7413`, `S7414`,
`S7418`, `S7420`.

### Macro arguments

For the standard macros whose arguments are all expressions (`assert!` and its
`_eq`/`_ne`/`debug_` forms, `println!`/`print!`/`eprintln!`/`eprint!`,
`format!`, `format_args!`, `write!`/`writeln!`, `panic!`, `unreachable!`,
`todo!`, `unimplemented!`, `dbg!`), sonda parses a second copy of the file in
which each `name!(` is `name (`: one space for the `!`, so every byte offset
and line is the original's, and the arguments read as a call. The rules run
on that copy too and keep what they find inside those arguments
(`rust_macros.rs`). Costs a second parse and query pass for a file that has
such a macro: about 0.1 s more over sonda's own 188 files.

On the corpus of batch 2 it took `identical-operands` from 25% to 75% recall
and `reversed-empty-range` from 44% to 78%, at the same precision. It also
showed what Clippy skips there: `assert_eq!(x, x)` is not an `eq_op` finding,
and neither is any operator on identical operands in test code.

Left out: `vec![]` and `matches!` (a bracket would read as an index, a
pattern isn't an expression), a log macro's `target:` argument, any macro of
a crate, and the body of a `macro_rules!`, where a value is a `$x:expr`
placeholder. A named format argument (`println!("{x}", x = x)`) reads as an
assignment, which `self-assignment` skips when it is an argument.

### Probing Clippy

The fourth batch (`rs_correctness.rs`) is 20 correctness lints whose
documentation is a sentence and an example: 9 new, and 11 of the third
batch's, rewritten. They deny by default, so published crates seldom contain
what they find: on 33 crates chosen for their patterns, Clippy reported 3 of
them. Instead, each lint was run, in the oracle's container, on probe files
written to vary its pattern, and the rules follow what it reported. They
agree on every probe line but one, a bound Clippy evaluates
(`x > i32::MAX - 1`) where sonda reads only literals, negated literals,
characters and constants with a literal value.


- `nonsensical_open_options` judges a chain only once it ends in `.open()`,
  and only literal `true`s: `read` with `truncate` and no `write`, `append`
  with `truncate`, and any option set twice.
- `bad_bit_mask` and `ineffective_bit_mask` follow their tables, with the
  constant on either side and through parentheses, and `x & 0` compared with
  anything is a bad mask. A named constant counts when the file declares it
  once: mio declares `POLLRDHUP` per `#[cfg]`, `0` on other systems, so it
  has no known value.
- `recursive_format_impl` reports formatting `self` with the trait being
  implemented, `{}` in `Display` and `{:?}` in `Debug`, whatever the width or
  position, through `write!`, `format!`, `println!` and the like, and
  `self.to_string()` in `Display`; not `fmt::Display::fmt(self, f)`.
- `unit_return_expecting_ord` covers the `*_by_key` sorts, searches, minimum
  and maximum and `select_nth_unstable_by_key`, not `dedup_by_key`, and a
  closure ending in `;`, `()`, `return;` or a print macro.
- `panicking_overflow_checks` is `a + b < a` and `a - b > a` and their
  mirrors, not `<=`, and leaves signed types alone; so does the rule where
  the file declares the operand signed or floating-point.
- `eager_transmute` needs the transmuted value to be the one the condition
  compares or tests with `contains`, and leaves integer targets alone.
- `size_of_in_element_count` needs the pointer to point to the `T` of
  `size_of::<T>()`, leaves `u8` alone, and doesn't cover `write_bytes`.
- `infinite_iter`'s sources are `(n..)`, `iter::repeat` and `.cycle()`, not
  `repeat_with`, `repeat_n` or `successors`. `map`, `filter`, `skip`,
  `enumerate`, `flat_map`, `by_ref` and `fuse` keep an iterator infinite;
  `chain` does with either side infinite and `zip` only with both;
  `step_by`, `peekable` and `inspect` end the lint's tracking. The consumers
  are `count`, `collect`, `sum`, `product`, `last`, `fold`, `for_each`,
  `partition` and the `min`/`max` family, through a turbofish too, not
  `find`, `position`, `any` or `nth` (`maybe_infinite_iter`'s). `repeat`
  must be `std::iter`'s: rayon has its own.
- `redundant_comparisons` and `impossible_comparisons` need two ordering
  comparisons against constants to be the operands of one `&&`, on the same
  expression without a call; not `==`, `||` or longer chains, and an empty
  open interval (`x > 5 && x < 6` on integers) isn't impossible to them.
- `match_str_case_mismatch` follows `to_lowercase`, `to_uppercase` and their
  ASCII forms through `&*`, `as_str()`, `as_ref()` and `[..]`, raw strings
  included and or-patterns left out.
- `mut_from_ref` needs `unsafe` code in the function, looks through
  `Option<&mut T>` and tuples, and skips a `'static` result and one whose
  lifetime a `&mut` input also has.
- `not_unsafe_ptr_arg_deref` counts a raw-pointer parameter as dereferenced
  when it's under `*`, an unsafe method's receiver (`p.add(1)`), or passed
  to an unsafe function: one the file declares `unsafe` or in an `extern`
  block, or one it doesn't declare. A trait impl's methods count as public,
  `pub(crate)` and a private module's don't, and a `let` shadowing the
  parameter ends its tracking.
- `panicking_unwrap` follows `is_none`/`is_some`/`is_ok`/`is_err` through
  `!` and `&&`, in `if` and `while` and their `else`, and stops at a
  shadowing `let`, an assignment and a closure.
- `while_float` needs a comparison with a float operand: a literal (`42f64`
  too), a cast, or a local declared or initialized as a float.
- `inherent_to_string_shadow_display` is `to_string(&self) -> String` and
  nothing else, beside a `Display` impl for the type, private or not.
- `non_octal_unix_permissions` is any decimal or hexadecimal literal given
  to `mode`, `set_mode` or `from_mode`, `0` and `7` too.

`run.py` now reports a lint that Clippy places inside a standard macro's
source (`write!`'s) at the crate's own call, where the rule reports it.

The rules' tests are those probe cases, each with what Clippy reported.
On the same probes, the third batch's versions of the 11 reported 15 lines
Clippy doesn't (an or-pattern arm, `x == 5 && x == 6`, `||`, `repeat_with`,
an `unwrap` after the value is shadowed, a `mut_from_ref` without `unsafe`)
and missed 55 it does, 24 of them pointer dereferences. On the corpus:

| Rule | Third batch | Rewritten |
|---|---|---|
| `unsafe-pointer-deref` | 0 of 15 found | 4 of 15, none wrong; 10 more in files Clippy didn't build, all correct on reading |
| `infinite-iterator` | 1 wrong (`repeat_n(..).collect()`) | none |
| `redundant-comparison` | 1 wrong (a pair inside a longer `&&` chain) | none |
| `mut-from-ref`, `to-string-shadows-display` | 1 of 1 each | 1 of 1 each |

The pointer findings still missed have a parameter whose pointer type is
an alias from another crate (`CFStringRef`), which one file can't resolve.

Cost: within noise of the scan without the batch, over the 693 crates of
the registry. That needed the `Hash`-and-`Borrow` rule's query narrowed to
`Hash` impls and derives (matching every attribute and searching the file
from each had cost 75%), and lookups of constants kept off function bodies.

### Open questions
- **Macros beyond the standard expression ones.** See "Macro arguments".
- **`cfg` blocks.** `#[cfg(...)]` items are all parsed, whichever
  configuration is active, unlike C#'s `#if` which can break parsing.
  Rules must not assume a name is unique across them.

## Consequences

- A fourth tree-sitter C grammar joins the isolated surface (Rust's
  scanner is small).
- The binary grows by the grammar's size, a few hundred KB; measured when
  the language lands, as it was for C#.
- Rust projects can move off SonarQube the same way the other languages
  can, for the 85 rules minus the gaps.
