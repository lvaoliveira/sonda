# ADR-0026: Rust support

- Status: **proposed**
- Date: 2026-11-04

## Context

The SonarQube rule parity effort ([ADR-0007](0007-sonarqube-rule-parity.md))
covers JavaScript/TypeScript, Python, Java, C/C++ and C#. SonarQube also
analyzes Rust, and, as with C#, its rule list and default profile come from
the same server the other languages are measured against: 85 rules, none
deprecated (60 bugs, 25 code smells), 78 of them in "Sonar way".

sonda doesn't parse Rust yet. Rules need a grammar, and the metrics
(functions, complexity, comments, duplication) need Rust's node kinds.

The list is short, and most of it is Clippy's lints under SonarQube keys:
`S7436` redundant comparisons, `S7437` manual swaps, `S7456` `skip(0)`,
`S7430` `splitn` with a limit of 0 or 1, and so on. Many of those compare
an operand's type, which a syntax tree doesn't carry. That sets the tiers
below.

sonda's own code is a corpus nobody else has: `sonar-project.properties`
already has SonarQube analyzing `crates/`, so each rule can be checked
against what SonarQube reports on the same commit.

## Decision

### Grammar

[tree-sitter-rust](https://github.com/tree-sitter/tree-sitter-rust) 0.24.2,
maintained by the tree-sitter organization:
- MIT licensed, like the other grammars;
- generated C plus an external scanner, so it joins the C surface worker
  isolation ([ADR-0003](0003-isolate-parsing.md),
  [ADR-0004](0004-sandbox-workers.md)) contains and the fuzzer exercises.
  The `analyze` fuzz target picks languages from `lang::ALL`, so it covers
  Rust once listed; a Rust seed joins the corpus;
- depends only on `tree-sitter-language`, already in the tree.

rust-analyzer or `rustc` would give real types, but need a toolchain and a
buildable project at scan time, which a single binary can't assume.

### The language

- `Lang::Rust`, id `rust`, for `.rs` files. It goes last in `lang::ALL`,
  whose order is a stable one-byte encoding.
- Metrics map Rust's declarations onto the shared `Syntax` table:
  `fn` items, methods, closures and `async` blocks are functions; `match`
  is a switch and its arms are cases (the `_` arm included, as in C#'s
  `default`: a decision to settle against SonarQube's own complexity).
- Rule ids are `rs/...`, in `rules/catalog/rs*.rs`.
- `scripts/sonar_parity.py` maps SonarQube's `rust` language to sonda's
  `rust`.

### Rules

ADR-0007 applies unchanged: clean-room rules from each SonarQube rule's
intent, `sonar` references by key, a false-positive review on real code, a
timing check, and on by default only when SonarQube's default profile
enables the key (so 78 of the 85).

By the analysis each rule needs, as a first guess ADR-0007 asks to confirm
as each is implemented:

- **Syntactic**, the bulk: empty statements, self-assignment, identical
  operands and `if`/`else if` conditions, missing final `else`, loops that
  run once, too many parameters, wildcard imports, `println!` as logging,
  cognitive complexity, `skip(0)`, `splitn(0|1)`, manual swaps,
  `visit_str` beside `visit_string`, syntax errors.
- **Declared types**, approximated the way C# does ([ADR-0015](0015-csharp.md)):
  a rule reports only what the file's own declarations prove and is
  `related` to its key when typed analysis would find more. For example
  `to_string()` on a `String`, redundant casts, `#[derive(Ord)]` beside a
  hand-written `PartialOrd`.
- **Left out on purpose**, listed as known gaps with the reason, as C# does,
  where a rule needs what only the compiler knows: which trait a method
  resolves to, `transmute` between layouts, whether a pointer's pointee is
  zero-sized.

The split is a guess from rule names. The first batch settles it; the known
gaps list, not this ADR, is the record of what was left out.

### Delivery

1. This ADR.
2. The language: grammar, `Lang::Rust`, metrics, file discovery, fuzz seed,
   the parity script's mapping and an empty catalog. Nothing reports yet.
3. Rules in batches of about 20, each reviewed on sonda's own `crates/`
   (compared with SonarQube's findings on that commit) and on a few open
   source crates, with a timing check.

### Open questions

- **Suppressions.** Whether SonarQube's Rust analyzer honors `#[allow(...)]`
  or `// NOSONAR`, and under which names. It decides whether sonda mirrors
  C#'s `#pragma`/`SuppressMessage` support or only its generic `NOSONAR`.
  Settled by testing against the server before rules ship.
- **Macros.** tree-sitter parses macro invocations as token trees, so code
  inside `println!(...)` or `vec![...]` isn't an expression tree. Rules
  needing arguments of well-known macros re-parse the tokens; the first
  batch decides how far that goes.
- **`cfg` blocks.** `#[cfg(...)]` items are all parsed, whichever
  configuration is active, unlike C#'s `#if` which can break parsing.
  Rules must not assume a name is unique across them.

## Consequences

- A fourth tree-sitter C grammar joins the isolated surface (Rust's
  scanner is small).
- The binary grows by the grammar's size, a few hundred KB; measured when
  the language lands, as it was for C#.
- Rust projects can move off SonarQube the same way the other languages
  can, for the 85 rules minus the gaps.
