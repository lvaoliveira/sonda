# ADR-0031: Go support

- Status: **accepted** for the language; the rules are a first batch
- Date: 2026-11-25

## Context

The roadmap lists Go, PHP, Ruby and Kotlin as the languages to add after the
SonarQube rule parity effort ([ADR-0007](0007-sonarqube-rule-parity.md))
covers the ones sonda has. Go is the first: a small, regular grammar, so the
metrics and rules are the cheapest to get right; widely used in the backend
and infrastructure code sonda users already scan; and `go vet`, staticcheck
and Effective Go give a settled idea of what a Go rule should report.

Unlike C# and Rust ([ADR-0015](0015-csharp.md), [ADR-0026](0026-rust.md)),
this one starts without a SonarQube Go rule list to measure against: the
parity lists in `docs/sonar-parity/` come from a SonarQube server, and none
with Go's analyzer has been compared yet. So the Go rules carry no SonarQube
key, and the parity table has no Go row.

## Decision

### Grammar

[tree-sitter-go](https://github.com/tree-sitter/tree-sitter-go) 0.25.0,
maintained by the tree-sitter organization, MIT licensed, and generated C
only (no external scanner), so it joins the C surface worker isolation
([ADR-0003](0003-isolate-parsing.md), [ADR-0004](0004-sandbox-workers.md))
contains and the fuzzer exercises. The `analyze` fuzz target takes its
languages from `lang::ALL`; a Go seed (`9`) joins the corpus.

### The language

- `Lang::Go`, id `go`, for `.go` files, last in `lang::ALL` (a stable
  one-byte encoding).
- Metrics: `func` declarations, methods and function literals are functions
  (as JavaScript's arrow functions are). `for` is the only loop; `switch`,
  type `switch` and `select` are switches, each case adding one. A `default`
  case adds nothing. Checked by hand against the definitions on a function
  with nested loops, `if`s and a `switch`: cyclomatic 7 and cognitive 15.
- A parameter list counts every name, not every declaration: Go's
  `a, b, c int` is three parameters. The other languages' declarations have
  one name, so counting names changes nothing for them.
- A file Go says it generated (`// Code generated ... DO NOT EDIT.` before the
  `package` clause, after any number of comment lines such as a license) is
  skipped as the other generated files are (`scan.skip_generated`). The
  scanner's general rule looks only at the first ten lines, which a license
  header can pass.
- Highlighting: Go's keywords and predeclared types, raw strings.
- The semantic layer ([ADR-0008](0008-semantic-layer.md)) has no Go binder
  yet, so the rules that need to know what a name refers to (unused
  variables, shadowing) and taint analysis wait for one.

### The rules

Twenty-three rules that the file's own text proves, with no types and no flow,
each with an example the test suite runs both ways:

- Bugs: `go/self-assignment`, `go/identical-operands`,
  `go/same-condition-in-chain`, `go/duplicate-case`, `go/defer-in-loop`,
  `go/empty-error-branch`, `go/unreachable-code`, `go/ignored-result`.
- Smells: `go/redundant-bool-literal`, `go/collapsible-if`,
  `go/empty-function`, `go/context-not-first`, `go/error-not-last`,
  `go/underscore-in-name`.
- Vulnerabilities, with CWE and OWASP: `go/hardcoded-credentials`,
  `go/weak-hash`, `go/weak-cipher`, `go/tls-unverified`, `go/weak-tls`,
  `go/sql-concatenation`, `go/shell-command`, `go/permissive-file-mode`,
  `go/ssh-insecure-host-key`.

Precision comes before recall, as everywhere in sonda:

- `x != x` on a name is Go's NaN test, so `go/identical-operands` leaves a
  name compared with itself alone.
- A call is matched by the package it was imported from (`md5.Sum` is
  `crypto/md5`'s only if the file imports it), so a local variable called
  `md5` isn't one. The query names the package and the function, so the
  import is looked up only for a call that could match: looking it up for
  every call made a 15,000-line file take ten seconds. A package imported
  under an alias isn't matched.
- A credential needs a name that says so (`password`, `secret`, `api_key`)
  and a value that could be one: not empty, not a template, not a sentence,
  and not a name about where it's read from (`passwordEnv`).
- `go/sql-concatenation` needs the text to read as SQL and a value joined to
  it.

Run on gin, cobra, chi, mux, client_golang and consul-template (about
120,000 lines), the rules report 100 or so findings, mostly in test files:
comparisons with `true` and `false`, collapsible `if`s and a `defer` in a
test loop, and in consul-template's real code three `InsecureSkipVerify`, two
MD5/SHA-1 uses and a `0666` file mode. No finding was wrong by the rule's own
text; whether a test's style matters is the team's to say (the usual way is
`exclude` in the configuration).

## Consequences

- Go files are scanned, measured and checked, and show in reports, SARIF and
  the web app (which takes its languages from the report).
- The rule list is a first batch, and not measured against SonarQube. When a
  SonarQube with Go's analyzer is available, the parity script gets a Go row
  and the rules are matched to its keys, as Rust's were.
- Taint analysis for Go (`net/http` handlers into `database/sql`,
  `os/exec` and `os.Open`) is the natural next step, and needs the binder.
- A Go package is a directory, so a rule across files of one package, as
  Java's are, is possible later.

## Alternatives

- **Wait for a SonarQube Go list before adding rules**: the parity effort is
  how sonda picks rules, but a list that can't be fetched shouldn't hold the
  language back, and these are rules `go vet` and staticcheck already agree
  are worth having.
- **A Go binder first**: it is the larger piece, and half of what makes Go
  code worth checking (errors ignored, `defer` misuse, SQL built from
  strings, weak crypto) is visible without names.
